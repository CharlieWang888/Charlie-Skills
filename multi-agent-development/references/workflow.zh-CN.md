# AI 多 Agent 自主软件开发工作流（V2.3）

**核心原则：Lead 根据任务和资源动态决定工程师人数，硬上限 5 名；超额任务进入 `QUEUED`；1 名独立审查员完成代码、测试和适用的 UI/UX 验收。任务状态可续接，证据真实，安全合并。**

本 Skill 适用于已有 Git 仓库的持续开发。尊重用户授权、仓库现有流程、平台工具与权限限制；不要把一次聊天会话误认为可无限运行的后台服务。

## 1. 角色与权限

| 角色 | 数量 | 允许 | 禁止 |
|---|---:|---|---|
| 项目经理 Lead（主会话） | 1 | 检查代码库、拆分和派单、更新任务状态、决定授权范围内的合并与清理、向用户汇报 | 编写业务代码；绕过审批或保护分支 |
| 工程师 Engineer | 0–5，由 Lead 按需决定，硬上限 5 | 独立分支/Worktree 开发、TDD、自测、修复、提交和推送 | 派第 6 名工程师；自行宣布 DONE；直接派单或合并受保护分支 |
| 审查员 Reviewer | 1 | 在固定 SHA 上独立检查规格符合性、代码质量、实际运行测试及适用的 UI/UX，输出结构化验收结论 | 修改业务代码、降低测试/UI 门禁、直接派单或合并 |

只有 Lead 调度任务并决定实际人数：根据依赖已满足的独立工作、文件所有权、审查吞吐、可用运行时槽位与成本确定 0–5 名 Engineer；**5 是绝对上限，不是要求开满**。人数需求超过 5 时将额外任务置为 `QUEUED` 并持久化优先级，不得启动第 6 名。工程师与审查员分别向 Lead 汇报；审查员不直接派修复。审查可为高风险任务建议额外专项专家，但必须由 Lead 在用户授权及实际可用容量内安排，不能取代唯一的独立最终 Reviewer。无法创建子 Agent 时标 `BLOCKED` 并请求用户调整，不得虚构团队或测试结果。

## 2. 启动与唯一数据源

**强制前置步骤：** Lead 立即读取真实系统时刻并开始计时，完整阅读 [仓库绑定与计时模板](repository-binding.md) 和现有根目录 `AGENTS.md`，按仓库明确的非托管时区规则（否则默认 `Asia/Tokyo` JST UTC+09:00）换算并输出真实启动时刻。在任何开发派单、业务代码修改或任务状态推进前，检查 Git 根目录 `AGENTS.md`：不存在则创建，已有则只新增/更新模板中标记的区块且保留其余规则；按授权提交并推送。未能安全持久化则标记 `BLOCKED` 并请求用户指示，不得静默跳过。任何再次调用本 Skill 也必须重检，避免重复插入。

1. 获取并核对仓库最新远端状态、默认分支、未合并工作和现有测试基线。
2. 阅读现有 `AGENTS.md`、`PRD.md`、路线图及任务文件；若名称不同，优先复用。缺少时根据已确认的仓库规则与用户需求建立精简版本；缺少需求或验收依据则先澄清，不自行推测产品范围。
3. 由 Lead 维护 `TASKS.md`（或仓库已有等价任务文件）。**只有 Lead 写入正式任务状态与负责人**，其他角色只提交结构化报告。关键状态变更必须 Commit/Push 到约定的共享分支，保持远端可续接；避免多个分支同时覆盖任务文件。
4. 每条任务必须包含：ID、目标、优先级、依赖、`READY/WAITING` 判定、负责人、**独占文件/模块所有权**、共享接口契约、验收标准与命令、`UI_SCOPE`、明确不做的范围、状态、分支、提交 SHA、审查记录及其证据链接。维护依赖关系/关键路径、调度与重大决策日志、会话恢复指针；记录哪些任务已排队及原因。
5. 所有 Agent 每次领取任务前重新读取适用的仓库规则和任务描述；不能依赖上一个会话的记忆。

### 计时和留痕（所有 Agent 强制）

- **统一时区（硬约束）：** Lead、Engineer、Reviewer、子任务、UI/UX Reviewer、`TASKS.md` 和最终报告的**所有新时间戳**必须使用仓库同一有效时区。优先遵循既有根 `AGENTS.md` 非托管段明确的 IANA 时区和 UTC 偏移（如 Knife-Zip 经用户确认的 `Asia/Shanghai` UTC+08:00），否则默认东京 `Asia/Tokyo`（JST，UTC+09:00）。以真实时钟取得事件瞬时点并换算；格式 `YYYY-MM-DD HH:MM:SS <offset> zone=<IANA-zone>`。若仓库时区规则含混或彼此冲突，标 `BLOCKED` 请求用户确认，禁止修改非托管规则或只替换偏移标签。
- **每轮启动：** 每个角色在实际开始时读取时刻，按仓库有效时区输出 `[START] role=... time=YYYY-MM-DD HH:MM:SS <offset> zone=<IANA-zone>`；Lead 立即启动本轮总计时。
- **每轮结束、暂停或阻塞：** 各角色输出换算成仓库有效时区的真实结束时间和本轮耗时 `HH:MM:SS`；Lead 同时输出当前总体历时。任何已完成且可测量的小任务额外记录同一时区的开始、结束及耗时。工时不因时区转换而改变。
- **总任务计时：** 首次启动时间以仓库有效时区记录到 `TASKS.md` 或现有任务台账；多轮续接不得重置。对历史其他合法偏移的首次启动时间，**保留原始瞬时点/出处，按需增加仓库时区的展示值，不得改变任务起点**。最终完成时以该时区展示首次开始、最终结束、总体墙钟历时；暂停与等待包含在内。另计活跃执行时间须单独标示，**不能把并行 Agent 的耗时相加当作总体历时**。
- **真实性：** 以实际可用系统时钟获取瞬时点、换算为仓库有效时区；跨时区历时用同一绝对时间轴相减，连续执行段尽量用单调时钟。不可准确取得的时间标 `NOT MEASURED` 及原因，不得倒填、伪造、仅改偏移标签，或声称对话结束后仍后台计时。格式以 [统一模板](repository-binding.md) 为准。

### 聊天 START 派工矩阵与 terminal final 逐角色耗时（V2.3 硬门禁）

**必须让用户在聊天主回复直接看见计时。** 仅把时间写进 `TASKS.md`、链接、工具日志或可能折叠的 commentary，不能替代最终可见答复。

1. **CHAT START dispatch matrix / 聊天 START 派工矩阵：** Lead 先在聊天显示自己实际测量的 `[START]`、`selected_engineers=N`（动态整数 0–5）及选择 N 的理由；再给可见表格：`Task | Status | Reason | Owner | Branch | Agent start`。逐任务显示 `READY / QUEUED / BLOCKED` 或 `NO_READY`，每行给真实依赖、文件所有权、Agent 槽位、审查容量或权限等具体理由。真实可独立执行任务不足时可选择 N=0，标明 `NOT STARTED`，绝不为了展示并行而派满五名或虚构 Agent。
2. **实际交接计时：** 每名 Engineer 和 Reviewer 各自在工作真正开始/结束时测量本人的 `[START]`/`[END]`，包含所在 `zone=`、UTC 偏移、任务、真实 elapsed。Lead 收到后在聊天向用户可见地转述，不能拿 Lead 的时间替代 Agent 时间。每项可测子任务也报真实起止/耗时，未测写 `NOT MEASURED` 和原因。
3. **VISIBLE TERMINAL FINAL / 每轮 terminal final 必填：** Lead 在**每轮最终答复**（包括暂停、阻塞、未完成轮次）给完整 `Role | Task/state | Start (zone) | End (zone) | Elapsed | Reason/evidence` 逐角色表：Lead、每个真实派发的 Engineer、Reviewer。未派 Engineer 写 `Engineer (none): NOT STARTED` 和原因；待审 Reviewer 写 `NOT STARTED`，未知真实时间写 `NOT MEASURED` 并解释。表下分别列出 `round_elapsed=`（本轮 Lead 起点→本轮终点）及 `first_scope_elapsed=`（首次范围起点→当前终点，包含轮间等待），并列真实起止时间及生效 IANA 时区。不得把并行 Agent 耗时相加当总历时。

此要求与 [repository-binding.md 的完整格式和可执行聊天断言](repository-binding.md)一致。用户无需打开台账即可看到每位角色进展与耗时；中途 partial final 和 commentary 不能替代末尾 terminal final。

### 状态机

| 状态 | 进入条件 |
|---|---|
| `TODO` | 已定义，尚未满足依赖或尚未进入可执行候选 |
| `QUEUED` | 依赖已满足，但因 Engineer/分支/Reviewer 容量或调度优先级暂不派发；保留优先级与入队原因 |
| `IN_PROGRESS` | Lead 已派发开发或返工 |
| `IN_REVIEW` | 工程师已推送、自测并提交证据 |
| `REJECTED` | 独立审查未通过，等待 Lead 派发修复 |
| `APPROVED` | 审查员确认约定验收标准已满足 |
| `BLOCKED` | 权限、环境、依赖或反复返工阻塞 |
| `DONE` | 已按授权合并，目标分支最终必需测试通过 |

严禁把“工程师完成”“审核通过”“合并成功”直接等同于 `DONE`。

## 3. Lead 的事件驱动循环

1. 从最新 `TASKS.md` 绘制依赖关系和关键路径，挑选依赖已满足且文件独立的最高优先级任务。Lead 明确决定本轮需要几名 Engineer（0–5），在 **聊天 START 派工矩阵** 可见地说明 `selected_engineers` 和依据；实际并行受运行时槽位、**最多 5 条活跃未合并任务分支**及 Reviewer 容量限制。多出的可执行任务置为 `QUEUED`，在台账**和聊天**记录入队原因和优先级，释放容量后重新评估。任何人都不得擅自新增第 6 名 Engineer。
2. Lead 先发送标准派单契约（下一节），再令每位工程师使用独立 Worktree 和 `feat/task-<id>` 分支；遵循适用的 TDD 与仓库约定，保留必要且准确的英文代码注释。共享文件指定唯一写入负责人、先确定接口，无法隔离时串行执行。
3. 工程师自测通过后提交、推送，报告变更摘要、分支、SHA、命令、退出码、测试计数，以及该 Agent 和小任务的开始/结束时间与耗时；Lead 将任务置为 `IN_REVIEW`。
4. 审查员在独立工作区检出固定 SHA，**第一轮核对需求/验收契约，第二轮检查代码质量、独立执行测试和适用的 UI/UX 验收**；允许测试生成临时产物，不得改受审业务代码。不采信工程师口头“全绿”或截图；只输出带证据的 `APPROVED`、`REJECTED` 或 `BLOCKED`。Lead 可先要求修正规格偏差，再启动完整质量复核，但不可跳过独立实测。
5. Lead 根据结论安排修复、执行已授权合并与合并后测试、更新任务状态，然后检查下一个可执行任务。

优先处理 Agent 完成事件，再用周期性的远端和任务文件核对防止遗漏；**不要建立无限高频轮询的 Sub-agent**。单条任务在 `IN_PROGRESS/IN_REVIEW/REJECTED/APPROVED` 且尚未合并时仍占一个活跃任务分支槽位；全项目**最多 5 条活跃未合并任务分支**。工程师空闲不自动代表可再开分支；审查积压时 Lead 优先完成验收/集成再从 `QUEUED` 派单。沟通使用任务专属消息，只有影响所有人的接口变更、阻塞或里程碑才广播。

### 派单契约、依赖和恢复台账（Lead 必填）

每次派单只发送当前任务可执行的上下文，至少含以下字段；不要整份 PRD 无差别转发，也不能依赖 Agent 的旧聊天记忆：

```text
Task ID / priority / dependencies / owner / branch
Goal and observable deliverable / requirements reference
Exclusive editable files and modules / shared files' single owner
Interface/API contract and integration assumptions
Acceptance: exact commands, expected result, platform, UI_SCOPE, UI/UX matrix
Out of scope / do-not-change / required evidence
Handoff: commit SHA, test exit codes/counts, findings, timestamps in effective repository timezone (Tokyo +09:00 by default)
```

Lead 在 `TASKS.md` 或现有等价文件维护：`TODO → QUEUED → IN_PROGRESS → IN_REVIEW → APPROVED → DONE`（返工经 `REJECTED`，阻塞经 `BLOCKED`）；任务依赖 DAG、关键路径、文件所有权表、排队原因、上次已审核 SHA、未合并分支清单、决策和阻塞日志，以及下一轮续接的确切动作。依赖尚未满足的任务保留 `TODO`，不得假装已就绪。两个工程师若需要修改同一共享接口/文件，先由 Lead 定唯一 owner 和接口契约，或者串行，不能在两个可写 Worktree 各自改同一文件后期待自动无冲突合并。

模型分工可由 Lead 依据任务复杂度、预算与实际运行时支持选择；**只使用当前工具真实支持的模型和参数**，不得复制他人的平台专用 Agent/TeamCreate 命令，或绕过既有权限。不得引入强制 GitHub Actions/付费 CI 依赖替代本地真实测试。

## 4. 独立、确定性的验收门禁

派单时先约定哪些命令、平台和 UI/UX 场景是必需的，再依据项目语言和平台执行对应检查：类型检查、Linter/静态分析、单元测试、集成与回归测试、完整构建，以及必要的 GUI/CLI/E2E、无障碍及系统专项测试。**任何涉及界面、交互、布局、可访问性、本地化或发布的任务必须先完整读取并执行 [UI/UX 独立验收规范](ui-ux-acceptance.md)。**

- 审查员必须**亲自运行工具**，记录完整命令、执行环境、提交 SHA、退出码、通过/失败/跳过数量。
- 任一必需检查退出码非零时直接判为 `REJECTED`；环境或权限导致无法执行时判为 `BLOCKED`，不能称“全绿”。
- 分成两轮独立评审：**规格/验收要求符合性**，以及**实现质量（功能逻辑、架构、边界、回归风险）与适用的 UI/UX**；不得把其中任一轮替代为工程师自述。
- 检查是否存在删除测试、弱化断言、改变测试数据或跳过测试以制造绿色结果的行为。
- 审查标准在派单前明确；不得事后降低、伪造输出或把跳过测试记为通过。
- 对 `UI_SCOPE=FULL`，Reviewer 在目标平台实际跑关键任务路径，做布局/DPI/文字缩放、交互、键盘/触控、可访问性、主题/长文本与异常状态检查，提交按维度评分的独立 UI/UX 报告及截图/视频/自动化日志。**合并须 ≥85/100、发布须 ≥90/100，且不得有 P0/P1 阻断项**；得分不能抵消硬门禁。`SMOKE` 走明确的 UI 冒烟，`NA` 说明原因且分数写 `NOT APPLICABLE`。具体矩阵、权重及报告字段见 [UI/UX 规范](ui-ux-acceptance.md)。
- 特定**必需**平台无法实测时逐项注明 `NOT RUN`、风险和 `BLOCKED`；不得把 Linux 测试冒充 Windows/iOS 实机验收。已实证失败的必需检查应 `REJECTED`，不能被其他通过项遮掩。

审查问题用 `P0 Critical / P1 High / P2 Medium / P3 Low` 标注，`P0/P1` 为阻断项。报告至少含：仓库有效时区的审查开始/结束时间与耗时、任务 ID、固定 SHA、规格符合性结论、独立测试命令/退出码/计数、复现步骤、相关文件、严重等级、预期/实际行为、环境、未测项目及建议。对 `FULL` UI 任务增加平台矩阵、证据、五维评分/总分、合并与发布结论。Reviewer 向 Lead 提交审查报告；**由 Lead 保存 `reviews/<task-id>-ui-ux.md` 或等价报告并从 `TASKS.md` 关联**，避免多人争写正式台账。审查员不修改任何业务文件。

## 5. 返工与阻塞

1. 审查员向 Lead 递交结构化结论，Lead 更新 `REJECTED` 并派单。
2. 默认由原作者修复以保留上下文；原作者正在忙则由 Lead 排期，不能让多个工程师竞争同一任务。
3. 每次返工必须重新自测、提交、推送并接受独立复审。
4. **同一任务连续被驳回超过两次**时转为 `BLOCKED`；Lead 重新分析、拆分或改派，必要时向用户请求决策。
5. 无法获得仓库权限、构建依赖、目标平台或人工批准时如实暂停，不擅自绕过。

## 6. Git 分支生命周期

- 遵守仓库现有默认、集成及发布分支策略；有 `dev` 则可作为日常集成分支，**不得擅自创建 `dev` 或改变既有发布流程**。
- 每任务一个短生命周期 `feat/task-<id>` 分支，同一任务的修复复用原分支；**每位工程师各用独立 Worktree，活跃未合并任务分支最多 5 条**。
- 功能自测通过后尽快 Commit/Push，审核固定到特定 SHA；未经审核不得合并。
- 由 Lead 在授权范围内合并 `APPROVED` 任务；**合并前必须核对待合并分支 HEAD 与审查员批准的 SHA 一致**，若已有新提交则重新审核新 SHA；合并后重新运行目标分支所有必需测试，全部通过才置 `DONE`。
- **只有确认变更已合并、目标分支测试通过且分支无独有未合并提交**，才允许清理对应本地/远端临时分支。移除 Worktree 前还须检查暂存、未暂存、未跟踪及忽略文件，存在独有数据就保留并报告，禁止强制删除。
- 永不自动清理 `main`、`dev`、`release/*`、明确保留的研究分支或未合并成果；不得强推、绕过保护规则或无授权合并发布分支。
- 保留提交 SHA、PR/MR、TASKS.md 和审核记录作为历史；定期检查已合并但未清理的分支。

## 7. 结束条件与汇报

仅当本轮范围所有任务均为 `DONE`、无遗留 `TODO/QUEUED/IN_PROGRESS/IN_REVIEW/REJECTED/BLOCKED`、所有代码已推送并按授权合并、集成分支必需测试全通过、适用的 UI/UX 合并/发布门禁通过且审查员提供最终结论时，才宣布完成并让 Agent 休息。遇到阻塞则说明未完成原因，保留可续接状态。

Lead 每轮阶段性汇报保持简洁，但 **terminal final 必须包含完整逐角色耗时表**（Lead、每位实际 Engineer、Reviewer；缺失/未开始行明确 `NOT MEASURED`/`NOT STARTED` 及理由），以及分开的 `round_elapsed=`、`first_scope_elapsed=`，不能只链接 `TASKS.md` 或依赖折叠 commentary。最终报告还必须包含：按仓库有效时区（默认 `Asia/Tokyo` +09:00）输出的本轮启动/结束时间及耗时、首次任务启动时间及总体历时、已完成子任务耗时、总/完成/`QUEUED`/`BLOCKED` 数量及具体原因、Lead 确认的动态 Engineer 人数与并发分支数、关键路径和阻塞决策、功能与 Bug 修复、独立测试命令及结果、UI/UX 矩阵/得分/阻断项、Git 分支与 SHA、合并及清理情况、审查结论、剩余风险和用户需要验收的内容。

**常见错误：**仍固定两名 Engineer，或把上限 5 当作必须派满；超过 5 不入队就擅派第 6 人；共享文件多人并改；Reviewer 不实测界面只看美观截图；用 85 分掩盖 P1；把缺失的 Windows/iOS 验收记为 PASS；任务状态只放聊天；在未合并前删分支；审核失败后跳过 Lead 私自派单。出现任一问题即停止相应状态推进并纠正。
