# AI 多 Agent 自主软件开发工作流（V1.0）

**核心原则：主会话统一调度，最多两名工程师并行，一名审查员独立验收；任务状态持久化，测试证据真实，分支及时安全清理。**

本 Skill 适用于已有 Git 仓库的持续开发。尊重用户授权、仓库现有流程、平台工具与权限限制；不要把一次聊天会话误认为可无限运行的后台服务。

## 1. 角色与权限

| 角色 | 数量 | 允许 | 禁止 |
|---|---:|---|---|
| 项目经理 Lead（主会话） | 1 | 检查代码库、拆分和派单、更新任务状态、决定授权范围内的合并与清理、向用户汇报 | 编写业务代码；绕过审批或保护分支 |
| 工程师 Engineer | 最多 2 | 独立分支/Worktree 开发、TDD、自测、修复、提交和推送 | 自行宣布 DONE；直接派单或合并受保护分支 |
| 审查员 Reviewer | 1 | 只读检查代码、独立运行测试、输出结构化验收结论 | 修改业务代码、降低测试标准、直接派单或合并 |

只有 Lead 调度任务。工程师与审查员分别向 Lead 汇报；审查员不直接向工程师派修复任务。无法创建子 Agent 时，立即说明能力限制，并请求用户调整执行方式，不要虚构团队或测试结果。

## 2. 启动与唯一数据源

1. 获取并核对仓库最新远端状态、默认分支、未合并工作和现有测试基线。
2. 阅读现有 `AGENTS.md`、`PRD.md`、路线图及任务文件；若名称不同，优先复用。缺少时根据已确认的仓库规则与用户需求建立精简版本；缺少需求或验收依据则先澄清，不自行推测产品范围。
3. 由 Lead 维护 `TASKS.md`（或仓库已有等价任务文件）。**只有 Lead 写入正式任务状态与负责人**，其他角色只提交结构化报告。关键状态变更必须 Commit/Push 到约定的共享分支，保持远端可续接；避免多个分支同时覆盖任务文件。
4. 每条任务必须包含：ID、目标、负责人、优先级、依赖、允许修改的模块/文件、验收标准与命令、状态、分支、提交 SHA、审查记录。
5. 所有 Agent 每次领取任务前重新读取适用的仓库规则和任务描述；不能依赖上一个会话的记忆。

### 状态机

| 状态 | 进入条件 |
|---|---|
| `TODO` | 已明确、尚未派发 |
| `IN_PROGRESS` | Lead 已派发开发或返工 |
| `IN_REVIEW` | 工程师已推送、自测并提交证据 |
| `REJECTED` | 独立审查未通过，等待 Lead 派发修复 |
| `APPROVED` | 审查员确认约定验收标准已满足 |
| `BLOCKED` | 权限、环境、依赖或反复返工阻塞 |
| `DONE` | 已按授权合并，目标分支最终必需测试通过 |

严禁把“工程师完成”“审核通过”“合并成功”直接等同于 `DONE`。

## 3. Lead 的事件驱动循环

1. 从最新 `TASKS.md` 找出依赖已满足的高优先级任务；派给最多两名工程师，确保修改文件或模块互不重叠；无法隔离时串行执行或先明确文件所有权。
2. 工程师使用独立 Worktree 和 `feat/task-<id>` 分支，遵循适用的 TDD 与仓库约定，保留必要且准确的英文代码注释。
3. 工程师自测通过后提交、推送，报告变更摘要、分支、SHA、命令、退出码和测试计数；Lead 将任务置为 `IN_REVIEW`。
4. 审查员在独立工作区检出明确 SHA 并执行验收；允许测试生成临时产物，但不得修改受审业务代码。不采信工程师口头“全绿”；只输出 `APPROVED`、`REJECTED` 或 `BLOCKED` 及证据。
5. Lead 根据结论安排修复、执行已授权合并与合并后测试、更新任务状态，然后检查下一个可执行任务。

优先处理 Agent 完成事件，再用周期性的远端和任务文件核对防止遗漏；**不要建立无限高频轮询的 Sub-agent**。工程师推送后可接受下一项独立任务，但全项目默认最多保留两个活跃、未合并的任务分支；审核积压时先处理验收与集成。

## 4. 独立、确定性的验收门禁

派单时先约定哪些命令是必需的，再依据项目语言和平台执行对应检查：类型检查、Linter/静态分析、单元测试、集成与回归测试、完整构建，以及必要的 GUI/CLI/E2E 或系统专项测试。

- 审查员必须**亲自运行工具**，记录完整命令、执行环境、提交 SHA、退出码、通过/失败/跳过数量。
- 任一必需检查退出码非零时直接判为 `REJECTED`；环境或权限导致无法执行时判为 `BLOCKED`，不能称“全绿”。
- 通过基础门禁后，再检查功能逻辑、架构、边界条件、需求覆盖及回归风险。
- 检查是否存在删除测试、弱化断言、改变测试数据或跳过测试以制造绿色结果的行为。
- 审查标准在派单前明确；不得事后降低、伪造输出或把跳过测试记为通过。
- 特定平台无法实测时逐项注明 `NOT RUN` 与风险；不得把 Linux 测试冒充 Windows/iOS 实机验收。

审查报告至少包含：任务 ID、SHA、结论、失败测试与退出码、复现步骤、相关文件、严重等级、预期行为、环境、未测项目及建议。审查员不修改任何业务文件。

## 5. 返工与阻塞

1. 审查员向 Lead 递交结构化结论，Lead 更新 `REJECTED` 并派单。
2. 默认由原作者修复以保留上下文；原作者正在忙则由 Lead 排期，不能让多个工程师竞争同一任务。
3. 每次返工必须重新自测、提交、推送并接受独立复审。
4. **同一任务连续被驳回超过两次**时转为 `BLOCKED`；Lead 重新分析、拆分或改派，必要时向用户请求决策。
5. 无法获得仓库权限、构建依赖、目标平台或人工批准时如实暂停，不擅自绕过。

## 6. Git 分支生命周期

- 遵守仓库现有默认、集成及发布分支策略；有 `dev` 则可作为日常集成分支，**不得擅自创建 `dev` 或改变既有发布流程**。
- 每任务一个短生命周期 `feat/task-<id>` 分支，同一任务的修复复用原分支；两位工程师各用独立 Worktree。
- 功能自测通过后尽快 Commit/Push，审核固定到特定 SHA；未经审核不得合并。
- 由 Lead 在授权范围内合并 `APPROVED` 任务；**合并前必须核对待合并分支 HEAD 与审查员批准的 SHA 一致**，若已有新提交则重新审核新 SHA；合并后重新运行目标分支所有必需测试，全部通过才置 `DONE`。
- **只有确认变更已合并、目标分支测试通过且分支无独有未合并提交**，才允许清理对应本地/远端临时分支。移除 Worktree 前还须检查暂存、未暂存、未跟踪及忽略文件，存在独有数据就保留并报告，禁止强制删除。
- 永不自动清理 `main`、`dev`、`release/*`、明确保留的研究分支或未合并成果；不得强推、绕过保护规则或无授权合并发布分支。
- 保留提交 SHA、PR/MR、TASKS.md 和审核记录作为历史；定期检查已合并但未清理的分支。

## 7. 结束条件与汇报

仅当本轮范围所有任务均为 `DONE`、无遗留 `REJECTED/BLOCKED`、所有代码已推送并按授权合并、集成分支必需测试全通过且审查员提供最终结论时，才宣布完成并让 Agent 休息。遇到阻塞则说明未完成原因，保留可续接状态。

Lead 每轮阶段性汇报保持简洁，最终报告至少包含：总/完成/剩余/阻塞任务数、功能与 Bug 修复、测试命令及结果、Git 分支与 SHA、合并及清理情况、审查结论、剩余风险和用户需要验收的内容。

**常见错误：**把“工程师说测试通过”当独立验收；同时修改同一工作树；任务状态只放聊天上下文；在未合并前删除分支；把缺失测试环境记为 PASS；审核失败后跳过 Lead 私自派单。出现任一问题即停止相应状态推进并纠正。
